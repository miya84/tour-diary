# 여행 수첩 구현 계획

제품 방향은 [PRODUCT.md](../../../PRODUCT.md)가 정한다. 1단계의 동작과 수용 기준은 [spec.md](spec.md)가 정하고, 2단계의 각 기능은 시작할 때 자기 스펙 폴더에서 정한다. 이 문서는 순서와 진행 상태만 안내한다. 둘이 다르면 스펙을 따른다.

## 진행 규칙

- **기능 1개 = 커밋 1개.** 기능 하나를 정하고, 구현하고, 검증한 뒤 바로 커밋한다. 커밋을 마친 다음에 다음 기능을 시작한다.
- **한 기능의 흐름:**
  1. 정하기: `shape-idea`로 `docs/specs/<기능 slug>/spec.md`를 쓴다. 화면이 있으면 프로토타입으로 먼저 확인한다.
  2. DB가 바뀌면 마이그레이션을 만들고, 적용 전에 SQL을 확인받는다.
  3. 구현: 순수 로직은 테스트를 먼저 쓴다.
  4. 검증: 타입 검사, lint, 단위 테스트, 실제 브라우저(폰 너비)에서 수용 기준을 확인한다.
  5. 커밋: Conventional Commits 형식(`feat: …`)으로 쓰고, 끝에 `Spec-Folder: docs/specs/<기능 slug>/`를 붙인다. 스펙 문서와 코드, 마이그레이션을 한 커밋에 담는다.
  6. 이 문서의 상태를 "완료"로 바꾼다.
- 기능 진행 중 범위가 바뀌면 그 기능의 스펙을 먼저 고치고 구현한다.
- 순서는 아래 제안을 따르되, 사용자가 바꿀 수 있다.

### 2-1. 유저 프로필과 닉네임

- **목표:** 프로필 화면에서 닉네임을 바꾸고, 앱 안에서 이메일 대신 닉네임으로 서로를 알아본다.
- **범위(제안):** 헤더에 닉네임을 표시하고 누르면 프로필 화면(`/profile`)으로 간다. 프로필에서 닉네임 수정, 이메일은 읽기 전용. 멤버 시트, 받은 초대("○○님이 초대했습니다"), 초대받은 여행 카드("○○님이 만든 여행")에 닉네임 표시. 초대는 계속 이메일로 한다.
- **정할 것:** 가입 때 닉네임을 받을지 이메일 앞부분을 기본값으로 쓸지(기존 계정 포함), 길이 제한과 중복 허용, 멤버 시트에 이메일을 함께 보일지.
- **작업:** `profiles` 테이블(닉네임, 이메일, 생성·수정 시각)과 가입 시 생성 트리거, 본인만 수정하는 RLS, 같은 여행 멤버끼리 닉네임을 읽는 규칙. 멤버 목록·받은 초대 함수가 닉네임을 돌려주게 변경. 프로필 화면. 프로젝트의 `setup-supabase` 스킬이 다루는 공식 프로필 패턴을 기준으로 한다.
- **완료 기준:** 닉네임을 바꾸면 헤더와 다른 멤버 화면(새로고침 후)에 바뀐 닉네임이 보인다. 다른 사람의 닉네임은 바꿀 수 없다.
- **결정(구현 시):** 가입 때 닉네임은 받지 않고 이메일 앞부분(최대 20자)을 기본값으로 넣는다(기존 계정도 채움). 길이는 1~20자, 중복은 허용한다. 멤버 시트에는 이메일을 보이지 않는다. 프로필 테이블에 이메일은 복사하지 않고(본인 이메일은 로그인 정보에서 읽는다), 컬럼 권한으로 닉네임만 수정할 수 있게 했다.
- **검증:** 닉네임 변경이 헤더·멤버 시트에 반영되는 것과 닉네임 외 컬럼의 수정 권한이 없는 것을 확인했다. 다른 계정의 화면(받은 초대, "○○님이 만든 여행")은 두 번째 계정으로 직접 확인하지 못했다.
- **커밋:** `feat: 유저 프로필과 닉네임 추가`

### 2-2. 예약함

- **목표:** 여행 중 QR 티켓, 바우처, 예약 확인 메일을 한곳에서 바로 꺼내 본다.
- **범위(제안):** 여행 화면에 "예약함" 탭. 예약 항목마다 제목, 종류(항공·숙소·교통·입장권 등), 날짜, 예약 번호, 메모, 첨부 이미지(QR 스크린샷·바우처)를 둔다. 예약 이메일은 본문 붙여넣기로 저장한다. 멤버 모두 보고 편집한다.
- **정할 것:** 첨부 형식(이미지만인지 PDF도인지)과 용량, 이메일을 붙여넣기로 할지 전달 받기로 할지(전달 받기는 범위가 크다), 일정 항목과 연결할지, 오프라인 열람은 PRODUCT.md상 핵심이 아니므로 제외할지.
- **작업:** 예약 테이블과 멤버 기준 RLS, Supabase Storage 버킷과 멤버만 읽는 정책, 예약함 탭·추가·보기 화면(QR을 크게 보여 주는 보기 포함).
- **완료 기준:** 멤버가 예약을 추가하고 첨부를 올리면 다른 멤버도 볼 수 있고, 멤버가 아닌 사람은 첨부 주소를 알아도 열 수 없다.
- **스펙:** [../trip-bookings/spec.md](../trip-bookings/spec.md). 첨부는 이미지만(10MB, 예약당 5개), 이메일은 메모에 붙여넣기, 일정과 연결하지 않는다.
- **커밋:** `feat: 여행 예약함 추가`

### 2-3. 다음 일정까지 남은 시간

- **목표:** 여행 중 다음 일정까지 시간이 충분한지 바로 확인한다.
- **범위(제안):** 일정 항목 사이에 이동 시간(구글 경로 계산)과 남는 시간을 표시한다. 시간이 부족하면 눈에 띄게 표시한다. 오늘 날짜면 "다음 일정"을 강조한다.
- **정할 것:** 이동 수단(대중교통·도보·차, 항목별 선택인지 기본값인지), 시작 시간이 없는 항목의 처리, 실제 도로 경로를 지도에 그릴지(1단계는 직선), 경로 계산 API 비용과 호출 시점.
- **작업:** Routes API 활성화(준비 항목), 일정 항목에 이동 수단 저장, 이동 시간 계산과 표시, 남은 시간 계산 로직 테스트.
- **완료 기준:** 시작 시간이 있는 연속된 두 항목 사이에 이동 시간과 남는 시간이 보이고, 부족하면 경고가 보인다.
- **커밋:** `feat: 다음 일정까지 남은 시간 표시`

### 2-4. 경비 기록

- **목표:** 여행 중 쓴 돈을 바로 적어 둔다.
- **범위(제안):** 여행 화면에 "경비" 탭. 항목마다 금액, 통화(엔·원), 낸 사람, 나눌 사람(기본은 멤버 전원), 날짜, 메모. 날짜별·전체 합계.
- **정할 것:** 통화와 환율(입력 시 고정 환율인지 직접 입력인지), 일정 항목과 연결할지, 카테고리를 둘지.
- **작업:** 경비 테이블과 멤버 기준 RLS, 경비 탭·추가·수정 화면, 합계 계산 로직 테스트.
- **완료 기준:** 멤버가 경비를 추가·수정·삭제하면 합계가 맞게 바뀌고 다른 멤버도 볼 수 있다.
- **커밋:** `feat: 여행 경비 기록 추가`

### 2-5. 경비 정산

- **목표:** 기록한 경비로 누가 누구에게 얼마를 보내면 되는지 바로 안다.
- **범위(제안):** 경비 탭에 정산 화면. 사람별로 낸 돈과 부담할 돈, 보낼 돈 목록(보내는 횟수가 적게). 정산 완료 표시.
- **정할 것:** 정산 통화(원으로 통일할지), 반올림 단위, 정산 완료 후 경비 수정을 막을지.
- **작업:** 정산 계산 로직(테스트 먼저), 정산 화면.
- **완료 기준:** 예시 경비 묶음에서 사람별 부담액 합계가 총액과 같고, 보낼 돈 목록대로 보내면 모두 0이 된다.
- **커밋:** `feat: 여행 경비 정산 추가`

### 2-6. 후보지 투표

- **목표:** 후보지가 갈릴 때 앱에서 투표로 정한다. 대화는 카톡에서 한다(PRODUCT.md 경계).
- **범위(제안):** 날짜(또는 시간대)별로 후보 묶음을 만들고 장소 후보를 올린다. 멤버마다 투표하고 결과를 본다. 정해진 후보를 일정 항목으로 옮긴다.
- **정할 것:** 1인 1표인지 여러 표인지, 마감 방식(직접 마감·시간 마감), 결과를 일정에 옮기는 방식(직접 옮기기인지 자동 반영인지. define-product에서 답을 받지 못한 점), 댓글은 두지 않는다(PRODUCT.md).
- **작업:** 투표·후보·표 테이블과 멤버 기준 RLS, 투표 화면, 후보를 일정으로 옮기는 동작.
- **완료 기준:** 멤버가 투표하면 결과가 보이고, 같은 사람이 같은 묶음에 규칙보다 많이 투표할 수 없으며, 정해진 후보가 일정 목록과 지도에 나타난다.
- **스펙:** [../trip-polls/spec.md](../trip-polls/spec.md). 투표는 질문 한 건과 후보 목록, 1인 1표(마감 전 변경 가능), 멤버 누구나 직접 마감, 마감하면 투표의 날짜 일정 맨 끝에 자동 반영(날짜는 만들 때 필수), 동률은 마감하는 사람이 고른다.
- **검증:** 폰 너비(375px)에서 AC1~AC4, AC6~AC10, AC12를 확인했다(투표 만들기·후보 올리기·표 옮기기·동률 마감 선택 막힘·마감 후 일정과 지도 핀 반영·삭제). 다른 멤버 계정에서 보기와 투표(AC5), 비멤버·내보낸 멤버 차단(AC11)은 두 번째 계정이 없어 직접 확인하지 못했다. 검증 중 만든 투표와 일정 항목은 지웠다.
- **커밋:** `feat: 후보지 투표 추가`

### 2-7. 실시간 반영

- **목표:** 다른 멤버가 바꾼 일정과 순서를 새로고침 없이 본다.
- **범위(제안):** 여행 화면에서 일정 항목 변경을 Supabase Realtime으로 받아 목록과 지도를 갱신한다. 예약함·경비·투표에도 같은 방식을 쓸지는 이때 정한다.
- **정할 것:** 반영 범위(일정만인지 전부인지), 순서 변경 중 다른 사람의 변경이 들어올 때의 처리, 동시 수정 충돌(지금은 나중 저장이 남는다).
- **작업:** 테이블 Realtime 활성화와 권한 확인, 구독과 화면 갱신.
- **완료 기준:** 두 브라우저에서 같은 여행을 열고 한쪽에서 일정을 추가·삭제·순서 변경하면 다른 쪽에 새로고침 없이 반영된다. 멤버가 아닌 사람은 변경을 받지 못한다.
- **스펙:** [../trip-realtime/spec.md](../trip-realtime/spec.md). 모든 탭의 변경을 반영하고, 수정 화면과 날짜별 순서 변경은 열려 있는 동안 다른 멤버가 못 고치게 잠근다(충돌 알림은 없음).
- **검증:** 같은 계정의 두 브라우저 탭으로 AC1~AC9를 확인했다(변경·삭제·투표 마감의 일정 반영, 항목 잠금과 해제, 날짜별 순서 잠금, 탭을 닫으면 잠금 해제). 비멤버 차단(AC10)과 폰 너비 화면, 예약·경비 수정 잠금(AC7)은 직접 확인하지 못했다.
- **커밋:** `feat: 일정 실시간 반영`
