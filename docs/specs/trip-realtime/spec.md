# 실시간 반영

다른 멤버가 바꾼 내용을 새로고침 없이 보고, 누군가 수정 중인 항목은 다른 멤버가 동시에 고치지 못하게 막는다.

제품 맥락: [PRODUCT.md](../../../PRODUCT.md) — "초대받은 사람만 한 여행을 함께 편집한다". 1단계 스펙의 미뤄 둔 결정(실시간 반영)을 되살린다.
용어: [GLOSSARY.md](../../../GLOSSARY.md)의 여행, 멤버, 일정 항목, 예약, 경비, 투표를 따른다.
순서와 진행 상태: [plan.md](../trip-day-route-map/plan.md)의 2-7.

연결된 결정 계약:
- [backend-platform](../../decisions/backend-platform.md) — 데이터와 동기화는 Supabase(Realtime)로 한다.
- [ui-composition](../../decisions/ui-composition.md) — 공식 shadcn component와 같은 상태 표현을 쓴다.

승인된 화면: 없음. 기존 화면에 잠금 표시(회색 처리와 "○○님이 수정 중" 문구)만 더한다.

## 사용자에게 보이는 결과

1. 두 멤버가 같은 여행을 열어 둔 상태에서 한쪽이 일정, 예약, 경비, 정산 완료 표시, 투표(후보·표·마감)를 바꾸면 다른 쪽 화면이 새로고침 없이 갱신된다. 지도와 목록 모두 같이 바뀐다.
2. 멤버가 일정 항목의 수정 화면을 열면, 다른 멤버 화면에서 그 항목의 수정 버튼이 눌리지 않고 "○○님이 수정 중"이 보인다. 수정 화면을 닫으면 풀린다.
3. 멤버가 일정 항목의 순서 변경을 시작하면, 다른 멤버 화면에서 그 날짜의 "순서 변경" 버튼이 눌리지 않고 "○○님이 순서 변경 중"이 보인다. 끝내면 풀린다.
4. 예약과 경비의 수정도 같다. 한 멤버가 수정 화면을 열면 다른 멤버는 그 예약 또는 경비를 수정할 수 없다.
5. 수정 화면을 연 채 브라우저 탭을 닫거나 연결이 끊기면 잠금은 저절로 풀린다.
6. 잠기지 않은 항목은 다른 멤버가 수정 중이어도 그대로 편집할 수 있다. 추가와 삭제는 잠그지 않는다.
7. 멤버가 아닌 사람과 내보내진 사람은 변경도 잠금 상태도 받지 못한다.

## 수용 기준

두 브라우저(또는 같은 브라우저의 두 탭)에서 같은 여행을 열고 확인한다. 폰 너비를 포함한다.

- AC1. 한쪽에서 일정 항목을 추가·수정·삭제하면 다른 쪽 일정 목록과 지도가 새로고침 없이 바뀐다.
- AC2. 한쪽에서 순서를 바꾸면 다른 쪽 목록과 지도 번호가 새로고침 없이 바뀐다.
- AC3. 예약, 경비, 정산 완료 표시, 투표(후보 올리기·표·마감)의 변경도 다른 쪽 화면에 새로고침 없이 반영된다. 투표를 마감하면 일정 탭에도 반영된다.
- AC4. 한쪽이 일정 항목 수정 화면을 열면 다른 쪽에서 그 항목의 수정이 막히고 누가 수정 중인지 보인다. 다른 항목은 수정할 수 있다.
- AC5. 한쪽이 수정 화면을 닫거나 저장하면 다른 쪽의 잠금이 풀린다.
- AC6. 한쪽이 순서 변경을 시작하면 다른 쪽에서 같은 날짜의 순서 변경이 막힌다. 다른 날짜의 순서 변경은 막히지 않는다.
- AC7. 예약과 경비의 수정 화면도 AC4~AC5와 같게 잠기고 풀린다.
- AC8. 수정 화면이 열린 탭을 닫으면 다른 쪽에서 잠금이 풀린다.
- AC9. 두 멤버가 동시에 같은 항목의 수정 화면을 열려고 하면 먼저 연 쪽만 잠금을 가진다(나중 쪽은 막힌다).
- AC10. 여행의 멤버가 아닌 계정은 잠금 채널에 들어가지 못하고, 다른 여행의 변경은 받지 않는다.

## 정한 것과 이유

- **반영 범위는 모든 탭.** 사용자가 정했다.
- **수정 중에는 막는다.** 사용자가 정했다. 충돌 때 알림(저장 전 버전 확인)은 넣지 않는다. 잠금이 있으면 같은 항목의 동시 수정이 막힌다.
- **잠금 단위는 항목 단위와 날짜별 순서 변경.** 사용자가 정했다. 일정 항목, 예약, 경비의 수정 화면과 하루의 순서 변경이 잠금 대상이다.
- **변경 수신은 Postgres Changes, 잠금은 Presence.** 에이전트 판단. 변경은 DB 행 변경을 그대로 받고, 잠금은 DB에 저장하지 않는다. 연결이 끊기면 자동으로 사라져 잠금이 남아 있는 일이 없다.
- **변경을 받으면 서버 데이터를 다시 불러온다(`router.refresh`).** 에이전트 판단. 화면이 쓰는 데이터 모양을 그대로 유지하고, 짧은 시간에 여러 변경이 오면 한 번만 불러온다.
- **잠금은 안내가 아니라 화면에서 막는 장치다.** 에이전트 판단(가정). 서버(RLS)는 잠금을 모른다. 세 명이 쓰는 앱이라 화면 잠금으로 충분하고, 연결이 끊긴 사이에는 나중 저장이 남는다.
- **동시에 잠그려 하면 먼저 잠근 쪽이 이긴다.** 에이전트 판단. 잠근 시각이 이른 쪽이 가진다.
- **잠금 채널은 여행 멤버만 들어간다(비공개 채널과 `realtime.messages` 정책).** 에이전트 판단. 닉네임과 수정 상태가 새어 나가지 않게 한다.

## 범위 밖과 이유

- 충돌 알림(버전 비교), 서버가 강제하는 잠금 — 사용자 결정과 위 이유.
- 투표 수정 잠금, 추가·삭제 잠금 — 수정 화면이 없거나 충돌 위험이 낮다.
- 다른 사람이 보고 있는 화면 표시(커서, 접속자 목록) — 요청 범위 밖.
- 오프라인에서 쌓은 변경의 병합 — PRODUCT.md 경계(오프라인은 핵심 가치가 아니다).

## 미뤄 둔 결정

- **서버 쪽 잠금 강제.** 되살리는 조건: 연결이 끊긴 사이의 덮어쓰기로 실제 데이터가 사라졌다는 일이 생길 때.
- **순서 변경 중 다른 멤버의 추가·삭제.** 되살리는 조건: 순서를 바꾸는 동안 목록이 바뀌어 곤란했다는 의견이 나올 때. 지금은 목록이 바뀌면 끌던 임시 순서를 버리고 최신 목록을 보인다.

## 남은 위험

- 비공개 채널을 강제하려면 Supabase 대시보드의 Realtime 설정에서 "Allow public access"를 꺼야 한다. 켜져 있으면 공개 채널은 열려 있지만, 이 앱은 비공개 채널만 쓰므로 잠금 채널의 접근 제어는 정책이 맡는다.
- 변경 알림은 DELETE에 대해서는 행 단위 권한 확인과 필터가 적용되지 않는다. 다른 여행의 삭제 알림이 도착할 수 있으나 내용은 행 id뿐이고, 받으면 다시 불러오기만 한다.
