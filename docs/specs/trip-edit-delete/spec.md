# 여행 제목·기간 수정과 여행 삭제

만든 사람이 여행의 제목과 기간을 고치고, 필요 없는 여행을 지운다.

제품 맥락: [PRODUCT.md](../../../PRODUCT.md) — "여행 계획을 여러 개 만들 수 있다"를 관리하는 조각이다. 1단계 스펙이 범위 밖으로 둔 "여행 제목·기간 수정, 여행 삭제"를 구현한다.
용어: [GLOSSARY.md](../../../GLOSSARY.md)의 여행, 멤버, 만든 사람, 일정 항목, 예약, 경비, 투표를 따른다.
순서와 진행 상태: [plan.md](../trip-day-route-map/plan.md)의 "2단계 밖의 후보".

연결된 결정 계약:
- [backend-platform](../../decisions/backend-platform.md) — 데이터는 Supabase에 저장한다. 첨부 파일도 같은 Supabase 안(Storage)에 둔다.
- [ui-composition](../../decisions/ui-composition.md) — 공식 shadcn component와 같은 상태 표현을 쓴다.

승인된 화면: 없음. 기존 시트와 확인 단계의 문법을 따르고 구현 뒤 실제 화면에서 검토한다.

## 사용자에게 보이는 결과

1. 여행 화면에서 **만든 사람**에게만 "여행 편집" 버튼이 보인다. 다른 멤버에게는 보이지 않는다.
2. 버튼을 누르면 시트가 열리고 현재 제목, 시작일, 종료일이 채워져 있다. 고쳐서 저장하면 여행 화면과 내 여행 목록이 바뀐다.
3. 기간을 줄여 기존 데이터가 새 기간 밖에 놓이면, 밖에 놓인 일정 항목, 경비, 투표는 새 기간의 가까운 끝 날짜로 옮겨진다. 새 시작일보다 앞선 것은 첫날로, 새 종료일보다 뒤인 것은 마지막 날로 간다. 옮겨진 일정 항목은 그 날짜 일정의 맨 끝에 원래 순서대로 붙는다.
4. 같은 시트 맨 아래의 "여행 삭제"를 누르면 확인 문구가 나오고, 한 번 더 확인하면 여행이 지워진다. 일정, 예약과 첨부 이미지, 경비, 정산, 투표, 멤버와 초대가 모두 함께 사라지고 되돌릴 수 없다는 점이 확인 문구에 보인다.
5. 삭제되면 내 여행 목록으로 돌아가고 목록에서 그 여행이 사라진다. 다른 멤버가 삭제된 여행을 열면 여행을 찾을 수 없는 화면이 나온다.
6. 만든 사람이 아니면 서버도 수정과 삭제를 거절한다.

## 수용 기준

실제 브라우저(폰 너비 포함)에서 확인한다.

- AC1. 만든 사람의 여행 화면에는 "여행 편집" 버튼이 보이고, 초대받은 멤버의 화면에는 보이지 않는다.
- AC2. 편집 시트에 현재 제목과 기간이 채워져 있다. 제목을 비우거나 종료일이 시작일보다 빠르면 저장되지 않고 이유가 보인다.
- AC3. 제목을 고쳐 저장하면 여행 화면 제목과 내 여행 목록의 제목이 바뀐다.
- AC4. 기간을 늘려 저장하면 새 날짜 탭이 생기고 기존 일정은 그대로다.
- AC5. 기간을 줄여 일정 항목이 새 기간 밖에 놓이면, 저장 후 그 항목이 가까운 끝 날짜의 맨 끝에서 원래 순서대로 보이고 사라지는 항목이 없다. 항목 수는 저장 전과 같다.
- AC6. 같은 경우의 경비와 투표도 가까운 끝 날짜로 옮겨져 경비 목록과 투표 카드에 보인다.
- AC7. 기간을 줄이는 폼에는 "기간 밖의 일정·경비·투표는 가까운 끝 날짜로 옮겨집니다"라는 안내가 보인다.
- AC8. 삭제를 누르면 확인 단계가 나오고, 취소하면 아무것도 지워지지 않는다. 확인하면 여행이 지워지고 내 여행 목록으로 간다.
- AC9. 삭제하면 그 여행의 예약 첨부 파일이 저장소에서도 지워진다.
- AC10. 초대받은 멤버가 서버 액션이나 API로 수정·삭제를 시도해도 거절된다(여행이 그대로 남는다).
- AC11. 폰 너비(375px)에서 편집 시트와 삭제 확인이 가로로 넘치지 않고 버튼이 보인다.

## 정한 것과 이유

- **수정과 삭제는 만든 사람만.** 사용자가 정했다. 지금 DB 규칙(여행 수정·삭제는 만든 사람 기준)과 같고 초대·내보내기와 같은 권한이다.
- **기간 밖의 데이터는 가까운 끝 날짜로 옮긴다.** 사용자가 정했다. 데이터가 사라지거나 화면에서 안 보이는 일이 없다.
- **삭제 확인은 확인 버튼 한 번.** 사용자가 정했다. 다른 삭제 동작(예약, 투표)과 같은 방식이다. 되돌릴 수 없다는 문구로 무게를 준다.
- **기간 수정과 데이터 이동은 DB 함수 한 번(`update_trip`)으로 한다.** 에이전트 판단. 여행 저장과 일정·경비·투표 이동이 함께 되거나 함께 안 되어야 한다.
- **예약의 날짜는 옮기지 않는다.** 에이전트 판단. 예약 날짜는 선택 항목이고 일정과 연결되지 않으며 화면이 날짜 탭에 묶여 있지 않다(예약함 스펙).
- **마감된 투표의 날짜는 옮기지 않는다.** 에이전트 판단. 이미 일정에 반영된 결과이고 날짜는 이력일 뿐이다. 진행 중인 투표만 옮긴다(마감하면 새 기간 안의 날짜에 들어가야 하기 때문).
- **삭제는 첨부 파일을 먼저 지운 뒤 여행을 지운다.** 에이전트 판단. 예약 삭제와 같은 순서다. 파일 삭제가 실패하면 여행을 지우지 않는다.
- **편집 버튼은 여행 화면에만 둔다.** 에이전트 판단(가정). 목록은 이동용으로 단순하게 둔다.

## 범위 밖과 이유

- 만든 사람 변경, 여행 복제, 삭제 취소(휴지통) — 요청 범위 밖.
- 기간을 줄이기 전에 옮겨질 항목 수를 미리 세어 보여 주기 — 안내 문구로 충분하다고 판단했다. 필요하면 다시 정한다.
- 삭제된 여행을 열어 둔 다른 멤버 화면의 즉시 반영 — 실시간 반영(2-7)이 병합된 뒤 여행 테이블을 구독에 넣으면 된다.

## 미뤄 둔 결정

- **옮겨질 항목 수 미리 보기.** 되살리는 조건: 기간을 줄였다가 뜻밖의 항목이 한 날에 몰려 곤란했다는 의견이 나올 때.
- **휴지통(삭제 취소).** 되살리는 조건: 실수로 지운 여행을 되살리고 싶다는 일이 생길 때.

## 남은 위험

- 기간 밖 데이터가 한쪽 끝날에 몰리면 그날 일정이 길어진다. 순서 변경으로 정리한다.
- 다른 멤버가 편집 중인 때 기간이 바뀌면, 그 멤버의 열린 화면은 새로고침 전까지 옛 날짜 탭을 보여 줄 수 있다.
